Redirect *.pages.dev traffic to the production domain after launch

Common misconception
Connecting a custom domain in Cloudflare Pages does not retire or redirect the .pages.dev URL. Both hostnames continue serving the same content indefinitely unless you take action. This was confirmed against the live site: curl -I https://alphabyte-ai.pages.dev/ still returns 200.
What's wrong today
Every page on alphabyte-ai.pages.dev returns <meta name="robots" content="index, follow"> and the preview's robots.txt is permissive (Allow: /). Canonical tags mostly point to the production domain, but three legal pages have no canonical (see Fix 02), so Google can index those preview URLs.
Two valid approaches
(A) 301 redirect from *.pages.dev to the matching path on alphabyte.ai. Cleanest. Preserves any existing backlinks. Once the custom domain is live, this is the standard recommendation.

(B) X-Robots-Tag noindex on the preview host. Keeps the preview accessible for QA but tells search engines not to index it. Use this if the team still wants to share preview URLs internally.

Pick one. Recommend A for a clean launch.
Why it matters
  • Preview can rank for branded searches and steal traffic from production.
  • Google splits signals between two hostnames serving identical content during the launch window.
  • Anyone who shared a preview link during development now sends traffic to a non-production URL forever.
▶ Paste into Claude Code from repo root (Option A: redirect)The site is a Next.js App Router app deployed to Cloudflare Pages. After connecting the custom domain alphabyte.ai, the original alphabyte-ai.pages.dev URL stays live (Cloudflare does not auto-redirect). I want a 301 redirect from every path on the preview host to the same path on the production host. Use Cloudflare Pages Bulk Redirects or a Cloudflare Rules → Single Redirect, configured in the Cloudflare dashboard, not in the repo. The rule: When hostname equals "alphabyte-ai.pages.dev" Then redirect to https://alphabyte.ai${path}${query} Status code: 301 Preserve query string: yes Repo-side, this means I do not need any code change for the redirect. But please add a one-line note to README.md under a "Deployment" section documenting that the redirect is configured at the Cloudflare level, so a future engineer doesn't try to undo it. In app/layout.tsx, conditionally emit robots: { index: false, follow: false } when the request hostname is not alphabyte.ai (read from headers in a Server Component, or check CF_PAGES_BRANCH / whichever env var the project actually exposes; check next.config.* and .env.example first to confirm). Pick whichever option I tell you to ship. Default to A (redirect).

What's wrong
Live response headers from the preview show only referrer-policy: strict-origin-when-cross-origin and x-content-type-options: nosniff. Missing: Strict-Transport-Security (HSTS), Content-Security-Policy, X-Frame-Options (or CSP frame-ancestors), Permissions-Policy, and Cross-Origin-Opener-Policy.
Where
public/_headers (Cloudflare Pages convention). Same file used in Fix 01. Bundle both into one PR.
Why it matters
  • Enterprise procurement teams run Mozilla Observatory or SecurityHeaders.com on every vendor before signing. Today this site scores D / F territory. After this fix it scores A.
  • HSTS is a one-line fix that protects every visitor from SSL-strip attacks and is required for SOC 2 / ISO 27001 questionnaires that mid-market clients increasingly send.
  • Without X-Frame-Options or CSP frame-ancestors, the site can be embedded in a phishing iframe.
